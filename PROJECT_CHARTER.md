# PROJECT CHARTER

**Проект:** AI Software Team

**Версия:** 0.1

**Статус:** Draft

---

# 1. Назначение документа

Настоящий документ определяет миссию проекта, область применения, стратегические цели, принципы развития и критерии успеха.

Все остальные документы проекта должны соответствовать настоящему Charter.

В случае возникновения противоречий между документами приоритет имеет следующий порядок:

1. PROJECT_CHARTER.md
2. AI_CONSTITUTION.md
3. AI_STANDARDS.md
4. Промпты агентов
5. Шаблоны документов
6. Примеры

---

# 2. Миссия проекта

Создать открытую библиотеку специализированных ИИ-агентов, способных совместно выполнять полный жизненный цикл разработки программного обеспечения.

Проект должен стать инженерной платформой, а не коллекцией отдельных промптов.

Каждый агент должен выполнять строго определенную роль и взаимодействовать с другими агентами через формализованные артефакты.

---

# 3. Видение

В долгосрочной перспективе AI Software Team должен позволять:

- проектировать программные продукты;
- выполнять системный анализ;
- создавать архитектуру;
- планировать разработку;
- писать качественный код;
- проводить автоматическое ревью;
- выполнять тестирование;
- готовить проекты к развертыванию;

без необходимости переписывать промпты при смене языковой модели.

---

# 4. Основные цели

## Цель 1

Создать единый стандарт взаимодействия между ИИ-агентами.

---

## Цель 2

Минимизировать неоднозначность принимаемых решений.

---

## Цель 3

Максимально разделить ответственность между агентами.

---

## Цель 4

Обеспечить воспроизводимость результатов.

---

## Цель 5

Подготовить основу для полностью автономной агентной системы.

---

# 5. Область применения

Проект предназначен для разработки:

- веб-приложений;
- мобильных приложений;
- настольных приложений;
- REST API;
- микросервисов;
- библиотек;
- CLI-инструментов;
- Telegram-ботов;
- корпоративных информационных систем;
- систем автоматизации;
- внутренних сервисов компаний.

---

# 6. Что проект НЕ делает

Проект не предназначен для:

- генерации случайного кода без требований;
- обхода процесса анализа требований;
- автоматического принятия бизнес-решений без участия пользователя;
- генерации архитектуры без входных данных;
- написания кода без утвержденной спецификации;
- замены экспертизы в предметной области.

---

# 7. Основные принципы

## 7.1 Разделение ответственности

Каждый агент отвечает только за собственную область компетенции.

---

## 7.2 Документирование

Любое принятое решение должно быть отражено в соответствующем документе.

---

## 7.3 Прослеживаемость

Любое архитектурное решение должно иметь источник.

Источник должен ссылаться на:

- требования;
- ограничения;
- пользовательские сценарии;
- бизнес-цели.

---

## 7.4 Минимизация предположений

Если информации недостаточно —

агент обязан запросить уточнение либо явно зафиксировать принятое допущение.

---

## 7.5 Объяснимость

Любое решение должно сопровождаться объяснением.

Ответ вида

> "потому что так лучше"

не допускается.

---

# 8. Архитектурные принципы

Все агенты обязаны придерживаться следующих инженерных принципов:

- SOLID
- DRY
- KISS
- YAGNI
- Separation of Concerns
- Clean Architecture
- Domain Driven Design (если применимо)
- Composition over Inheritance
- Fail Fast
- Explicit is Better than Implicit

---

# 9. Независимость моделей

Проект не должен зависеть от конкретной языковой модели.

Допускается использование:

- GPT
- Claude
- Gemini
- Qwen
- DeepSeek
- Llama
- Mistral
- иных современных LLM.

Все промпты должны быть написаны максимально переносимо.

---

# 10. Артефакты проекта

Каждый этап разработки обязан создавать собственный артефакт.

Примеры:

- requirements.json
- SRS.md
- architecture.md
- roadmap.json
- review.md
- test_report.md
- deployment.md

Артефакты являются единственным способом передачи информации между агентами.

---

# 11. Критерии качества

Каждый агент обязан стремиться к следующим характеристикам результата:

- полнота;
- непротиворечивость;
- воспроизводимость;
- проверяемость;
- расширяемость;
- читаемость;
- документированность.

---

# 12. Definition of Done

Работа считается завершенной только при выполнении всех условий:

- выполнены требования;
- отсутствуют известные критические ошибки;
- подготовлены необходимые документы;
- соблюдены стандарты проекта;
- сформированы выходные артефакты;
- агент выполнил самопроверку.

---

# 13. Принципы развития проекта

При развитии проекта допускается:

- добавление новых агентов;
- изменение шаблонов документов;
- расширение схем данных;
- улучшение внутренних стандартов.

Не допускается:

- нарушение совместимости существующих артефактов без изменения версии;
- изменение ответственности существующих агентов без обновления документации.

---

# 14. Версионирование

Проект использует Semantic Versioning.

MAJOR — несовместимые изменения.

MINOR — новая функциональность.

PATCH — исправления и уточнения.

---

# 15. Успех проекта

Проект считается успешным, если:

- все агенты работают согласованно;
- результаты одного агента могут быть использованы следующим без ручной переработки;
- пользователь может пройти полный цикл разработки, последовательно используя документы проекта;
- библиотека остается независимой от конкретной LLM и пригодна для интеграции в будущие оркестраторы.

---

# 16. Заключение

AI Software Team рассматривает разработку программного обеспечения как совместную работу специализированной команды экспертов.

Каждый агент является самостоятельным профессионалом, но только совместная работа всей команды позволяет получить качественный, воспроизводимый и инженерно обоснованный результат.
