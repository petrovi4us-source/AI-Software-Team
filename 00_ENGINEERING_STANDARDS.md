# Глава 1. Общие положения и терминология

## 1.1 Назначение документа

Настоящий документ определяет единые инженерные стандарты проекта AI Software Team.

Документ устанавливает:

- архитектурную модель агентной системы;
- правила организации процесса разработки;
- требования к качеству инженерных решений;
- правила формирования и передачи артефактов;
- единый словарь терминов;
- обязательные требования к работе всех агентов.

Настоящий стандарт является нормативным документом проекта.

Все агенты AI Software Team обязаны соблюдать требования настоящего документа.

---

# 1.2 Область применения

Настоящий стандарт применяется ко всем этапам жизненного цикла разработки программного обеспечения:

- сбор требований;
- анализ требований;
- проектирование архитектуры;
- планирование разработки;
- реализация программного кода;
- проверка качества;
- тестирование;
- подготовка к развертыванию;
- сопровождение.

Стандарт применяется независимо от:

- используемой языковой модели;
- программного языка;
- платформы разработки;
- области применения создаваемого продукта.

---

# 1.3 Архитектурная модель AI Software Team

AI Software Team использует четырехуровневую архитектурную модель:
Stage

↓

Contract

↓

Agent

↓

Artifact

Каждый уровень имеет строго определенное назначение.

---

## Stage

Stage — этап жизненного цикла разработки.

Stage определяет:

- цель этапа;
- место этапа в общем процессе разработки;
- необходимые входные данные;
- ожидаемый результат;
- критерии начала;
- критерии завершения.

Примеры Stage:

- Requirements Discovery Stage;
- Requirements Analysis Stage;
- Architecture Design Stage;
- Implementation Stage;
- Testing Stage.

---

## Contract

Contract — формальное описание взаимодействия между этапами.

Contract определяет:

- какие данные получает этап;
- какие данные формирует этап;
- требования к входным данным;
- требования к выходным данным;
- критерии приемки результата.

Contract является интерфейсом между этапами разработки.

Изменение контракта требует проверки совместимости всех связанных этапов.

---

## Agent

Agent — специализированный исполнитель, реализующий один или несколько контрактов.

Agent отвечает за выполнение конкретной инженерной функции.

Agent:

- получает входные артефакты;
- выполняет обработку;
- создает выходной артефакт;
- выполняет самопроверку результата.

Agent не изменяет область ответственности других агентов.

---

## Artifact

Artifact — результат выполнения этапа.

Artifact является единицей обмена информацией между агентами.

Примеры артефактов:

- requirements.json;
- SRS.md;
- architecture.md;
- roadmap.json;
- source code;
- review.md;
- test_report.md;
- deployment.md.

Каждый Artifact должен иметь:

- владельца;
- версию;
- статус;
- источник происхождения.

---

# 1.4 Принцип разделения ответственности

Каждый элемент архитектурной модели имеет собственную ответственность.
Stage

Определяет ЧТО должно быть выполнено.

↓

Contract

Определяет КАК осуществляется взаимодействие.

↓

Agent

Определяет КТО выполняет работу.

↓

Artifact

Определяет ЧТО является результатом.

Смешивание этих уровней запрещается.

Примеры неправильного подхода:

- описание требований внутри промпта агента вместо Contract;
- хранение решений только в сообщении чата вместо Artifact;
- изменение процесса разработки внутри конкретного Agent.

---

- предложить способ разрешения.

# 1.6 Основные инженерные принципы

Все решения проекта должны соответствовать следующим принципам.

---

## Прослеживаемость

Каждое решение должно иметь источник.

Допустимые источники:

- требование пользователя;
- бизнес-требование;
- техническое ограничение;
- архитектурное решение;
- стандарт проекта.

---

## Проверяемость

Каждый результат должен иметь критерии проверки.

Непроверяемые утверждения не могут считаться инженерными решениями.

---

## Воспроизводимость

При одинаковых входных данных процесс должен приводить к сопоставимому результату.

---

## Минимизация предположений

Если информации недостаточно, Agent обязан:

- запросить уточнение;
- либо оформить явное допущение.

Скрытые допущения запрещаются.

---

## Простота

Из нескольких решений предпочтение получает решение с минимальной сложностью при сохранении требований.

---

## Согласованность

Все Artifact проекта должны использовать:

- одинаковые термины;
- одинаковые идентификаторы;
- одинаковые правила оформления.

---

# 1.7 Терминология

## Проект

Совокупность всех Artifact, решений, исходного кода и процессов, направленных на создание программного продукта.

---

## Пользователь

Человек, который формирует требования, принимает ключевые решения и подтверждает результаты этапов.

---

## Требование

Описание необходимого свойства или поведения системы.

Требование должно быть:

- однозначным;
- проверяемым;
- непротиворечивым.

---

## Ограничение

Условие, которое уменьшает множество допустимых решений.

Примеры:

- бюджет;
- сроки;
- технология;
- законодательные требования.

---

## Допущение (Assumption)

Предположение, принятое при отсутствии полной информации.

Каждое допущение должно содержать:

- описание;
- причину;
- влияние;
- необходимость подтверждения.

---

## Риск

Возможное событие, которое может отрицательно повлиять на проект.

Риск описывается через:

- вероятность;
- влияние;
- стратегию снижения.

---

## Решение

Осознанный выбор одного варианта из нескольких возможных.

Инженерное решение должно содержать:

- контекст;
- варианты;
- выбранный вариант;
- обоснование;
- последствия.

---

## ADR (Architecture Decision Record)

Документированная запись архитектурного решения.

ADR содержит:

- проблему;
- контекст;
- варианты;
- принятое решение;
- последствия.

---

## Технический долг

Будущее обязательство по улучшению системы, возникшее из-за принятия упрощенного решения.

Каждый технический долг должен быть:

- зафиксирован;
- объяснен;
- оценен.

---

## Definition of Ready (DoR)

Набор критериев, определяющих готовность начала Stage.

---

## Definition of Done (DoD)

Набор критериев, определяющих завершение Stage.

---

# 1.8 Требования к терминологии

Все документы проекта обязаны использовать единый словарь.

Запрещается:

- вводить новые термины без необходимости;
- использовать разные термины для одного понятия;
- применять разговорные выражения в инженерных документах.

При введении нового термина он должен быть добавлен в настоящий раздел.

---

# 1.9 Версионирование

Все документы и Artifact должны поддерживать версионирование.

Рекомендуется использовать Semantic Versioning:

MAJOR.MINOR.PATCH

Где:

MAJOR — несовместимые изменения.

MINOR — новая функциональность.

PATCH — исправление ошибок.

# 1.10 Требования к инженерным документам

Каждый нормативный документ проекта должен содержать:

- назначение;

AI Software Team использует последовательную модель разработки.

Каждый этап является самостоятельным Stage.

Каждый Stage реализуется через Contract.

Contract выполняется Agent.

Результатом выполнения является Artifact.

Общая схема:
Stage

↓

Contract

↓

Agent

↓

Artifact

↓

Следующий Stage

---

# 2.3 Общие правила жизненного цикла

Каждый Stage обязан иметь:

- уникальное название;
- назначение;
- входные Artifact;
- выходные Artifact;
- Contract;
- Agent;
- Definition of Ready;
- Definition of Done.

Stage не может быть начат без выполнения Definition of Ready.

Stage не может считаться завершенным без выполнения Definition of Done.

# Глава 3. Архитектурная модель Agent-Contract-System

## 3.1 Назначение главы

Настоящая глава определяет архитектуру взаимодействия между Stage, Contract, Agent и Artifact.

Цель модели:

- обеспечить заменяемость агентов;
- отделить процесс разработки от конкретной реализации;
- обеспечить масштабирование агентной системы;
- подготовить основу для автоматизации взаимодействия агентов.

---

# 3.2 Основной архитектурный принцип

AI Software Team использует принцип:

> Contract First Architecture

Это означает:

Сначала определяется контракт взаимодействия.

После этого выбирается агент, который реализует данный контракт.

Агент является реализацией контракта, а не основой архитектуры.

---

# 3.3 Общая архитектура

Модель системы:
                Stage

                  │

                  ▼

              Contract

                  │

                  ▼

          Agent Implementation

                  │

                  ▼

              Artifact
              
---

# 3.4 Уровень Stage

Stage представляет собой логический этап жизненного цикла разработки.

Stage определяет:

- цель;
- последовательность выполнения;
- критерии начала;
- критерии завершения.

Stage не зависит от конкретного Agent.

Пример:
Architecture Design Stage
может быть выполнен:

- одним Architect Agent;
- группой специализированных агентов;
- автоматизированной системой.

---

# 3.5 Уровень Contract

Contract является главным элементом взаимодействия системы.

Contract определяет интерфейс между этапами.

Каждый Contract должен содержать:

- название;
- версию;
- назначение;
- входные данные;
- выходные данные;
- ограничения;
- критерии качества;
- правила проверки.

---

  - components_defined
  - decisions_documented

**#3.6 Правила проектирования Contract**

Contract должен быть:

Однозначным
Нельзя допускать различные трактовки входов и выходов.

Минимальным
Contract должен содержать только необходимые данные.

Стабильным
Изменение Contract должно происходить реже, чем изменение Agent.

Расширяемым
Новая функциональность должна добавляться без разрушения существующей совместимости.

**# 3.7 Уровень Agent**

Agent является исполнителем Contract.

Agent отвечает за:

обработку входных Artifact;
выполнение логики этапа;
создание выходного Artifact;
проверку результата.

Agent не определяет:

последовательность жизненного цикла;
формат взаимодействия;
правила передачи данных.

Эти функции принадлежат Stage и Contract.

**# 3.8 Реализация Agent**

Каждый Agent должен иметь:

название;
назначение;
реализуемый Contract;
входные данные;
выходные данные;
ограничения;
правила поведения;
критерии качества;
процедуру самопроверки.

**## Пример**

Agent:

Architecture Agent


Implements:

Architecture Design Contract


Input:

SRS.md


Output:

architecture.md

**# 3.9 Замена Agent**
Один Contract может иметь несколько реализаций.

**## Пример:**
Architecture Design Contract

        │

        ├── GPT Architecture Agent

        ├── Claude Architecture Agent

        └── Human Architect
Все реализации должны выдавать совместимый Artifact.

**# 3.10 Совместимость Agent**

Agent считается совместимым с Contract если:

принимает необходимые входные данные;
создает требуемый выходной Artifact;
соблюдает критерии качества;
выполняет правила проекта.

**# 3.11 Композиция Agent**

Сложный Stage может использовать несколько Agent.

**## Пример:**
Architecture Stage

        │

        ├── Backend Architect

        ├── Security Architect

        └── Database Architect

                │

                ▼

          architecture.md
В этом случае несколько Agent реализуют один общий Contract.

**# 3.12 Уровень Artifact**

Artifact является физическим результатом выполнения Contract.

Artifact должен быть:

машиночитаемым или структурированным;
версионируемым;
проверяемым;
передаваемым.

**# 3.13 Правила Artifact**

Каждый Artifact должен содержать:

## Метаданные
название;
версия;
статус;
создатель;
дата создания.

**## Содержание**
результат выполнения Stage;
необходимые пояснения;
ссылки на источники.

**## Контекст**

Artifact должен отвечать на вопросы:

почему он создан;
на основании чего;
кем;
для какого следующего Stage.

**# 3.14 Версионирование Contract**

Contract должен иметь версию.

Используется Semantic Versioning:
MAJOR.MINOR.PATCH

**## MAJOR**

Изменение нарушает совместимость.

Пример:

Было:
Input:
SRS.md

Стало:
Input:
requirements.json

**## MINOR**

Добавляется новая возможность без нарушения совместимости.

**## PATCH**

Исправляются ошибки описания.

**## 3.15 Изменение Contract**

Перед изменением Contract необходимо:

определить зависимые Stage;
определить зависимые Agent;
оценить влияние;
создать новую версию.

**## 3.16 Будущий Orchestrator Layer**

Архитектура Agent-Contract-System подготовлена для добавления Orchestrator.

Будущая схема:

``` id="eqx6d2"
              User

               │

               ▼

          Orchestrator

               │

               ▼

            Stage

               │

               ▼

          Contract

               │

               ▼

            Agent

               │

               ▼

          Artifact

Orchestrator не выполняет инженерную работу.

Его ответственность:

- запуск Stage;
- передача Artifact;
- контроль состояния;
- обработка ошибок;
- управление версиями.

---

# 3.17 Принцип отсутствия зависимости

Stage не должен зависеть от конкретного Agent.

Agent не должен зависеть от предыдущего Agent.

Связь осуществляется только через Contract и Artifact.

---

# 3.18 Итог главы

После изучения настоящей главы Agent должен понимать:

- архитектуру Agent-Contract-System;
- роль каждого уровня;
- правила создания Contract;
- правила разработки Agent;
- правила работы с Artifact;
- принципы совместимости;
- подготовку системы к оркестрации.



# Глава 4. Принятие инженерных решений и Decision Framework


## 4.1 Назначение главы

Настоящая глава определяет единый процесс принятия инженерных решений в AI Software Team.

Цели Decision Framework:

- обеспечить обоснованность решений;
- уменьшить влияние субъективных предположений;
- обеспечить прозрачность выбора;
- обеспечить возможность пересмотра решений;
- сохранить историю развития проекта.

Все значимые инженерные решения должны приниматься согласно настоящему Framework.


---

# 4.2 Принцип инженерного решения


Инженерное решение — это документированный выбор одного варианта реализации из нескольких возможных вариантов.


Решение считается инженерным только если содержит:

- контекст;
- проблему;
- возможные варианты;
- критерии оценки;
- выбранное решение;
- последствия.


Формула:
Decision =
Context +
Problem +
Options +
Evaluation +
Choice +
Consequences


---

# 4.3 Типы решений


В AI Software Team используются следующие типы решений.


## Архитектурное решение

Решение, влияющее на структуру системы.


Примеры:

- выбор архитектурного стиля;
- выбор базы данных;
- выбор способа интеграции;
- распределение компонентов.


Требует ADR.


---

## Технологическое решение

Выбор конкретной технологии.


Примеры:

- язык программирования;
- библиотека;
- framework;
- инфраструктурный инструмент.


---

## Реализационное решение

Решение внутри программного кода.


Примеры:

- структура класса;
- алгоритм;
- паттерн проектирования.


---

## Процессное решение

Изменение способа работы команды или агентов.


Примеры:

- изменение Contract;
- изменение Stage;
- изменение правил проверки.


---

# 4.4 Уровни значимости решений


Не все решения требуют одинакового уровня анализа.


Используются три уровня.


## Level 1 — Локальное решение


Влияние ограничено одним компонентом.


Примеры:

- имя переменной;
- структура небольшого метода.


Документирование не требуется.


---

## Level 2 — Техническое решение


Влияние распространяется на несколько компонентов.


Примеры:

- выбор библиотеки;
- изменение API;
- изменение структуры данных.


Рекомендуется документирование.


---

## Level 3 — Архитектурное решение


Влияет на систему в целом.


Примеры:

- выбор архитектуры;
- изменение модели данных;
- изменение Contract.


Обязательно создание ADR.


---

# 4.5 Decision Framework


Каждое значимое решение должно проходить следующие этапы.

Context

↓

Problem

↓

Requirements

↓

Options

↓

Evaluation

↓

Decision

↓

Consequences

↓

Validation


---

# 4.6 Context


Контекст описывает ситуацию, в которой принимается решение.


Должен содержать:

- текущее состояние;
- ограничения;
- существующие зависимости;
- заинтересованных участников.


Пример:
Система должна обрабатывать 10000 запросов в минуту.
Текущая архитектура не обеспечивает необходимую производительность.


---

# 4.7 Problem


Проблема должна быть сформулирована без указания решения.


Неправильно:
Нужно использовать PostgreSQL.


Правильно:
Необходимо выбрать систему хранения данных,
обеспечивающую транзакционность и горизонтальное масштабирование.


---

# 4.8 Requirements


Перед выбором решения должны быть определены критерии.


Примеры критериев:

- стоимость;
- производительность;
- надежность;
- безопасность;
- сложность поддержки;
- время разработки;
- совместимость.


---

# 4.9 Options


Перед выбором решения необходимо рассмотреть альтернативы.


Минимально:

- выбранный вариант;
- минимум одна альтернатива.


Для архитектурных решений рекомендуется рассматривать минимум три варианта.


---

# 4.10 Evaluation


Варианты должны оцениваться по одинаковым критериям.


Пример:


| Критерий | Вариант A | Вариант B |
|-|-|-|
| Стоимость | + | - |
| Масштабирование | + | + |
| Сложность | - | + |


---

# 4.11 Decision


Выбранное решение должно содержать:

- конкретный вариант;
- причину выбора;
- связь с требованиями.


Запрещается формулировка:
Выбрано потому что это лучше.


Допустимо:
Выбран вариант A,
так как он удовлетворяет требованиям X и Y
при меньшей сложности реализации.


---

# 4.12 Consequences


Каждое решение имеет последствия.


Необходимо указать:


## Положительные последствия

Что улучшилось.


## Отрицательные последствия

Какие появились ограничения.


## Будущие риски

Что необходимо контролировать.


---

# 4.13 Validation


После принятия решения должна существовать проверка.


Типы проверки:

- тестирование;
- прототипирование;
- анализ производительности;
- экспертная проверка.


---

# 4.14 Architecture Decision Record (ADR)


Для Level 3 решений используется ADR.


Структура ADR:


```markdown
# ADR-XXX Название


## Status

Accepted


## Context

Описание ситуации.


## Problem

Описание проблемы.


## Options

Рассмотренные варианты.


## Decision

Принятое решение.


## Consequences

Последствия.


## Validation

Способ проверки.

**# 4.15 Правила работы Agent с решениями**

## Agent обязан:

отделять факты от предположений;
указывать неизвестные данные;
рассматривать альтернативы;
объяснять причины выбора;
фиксировать риски.

## Agent запрещено:

выдавать мнение как факт;
скрывать ограничения;
выбирать технологию без критериев;
создавать необоснованные архитектурные решения.

---

**# 4.16 Работа с неопределенностью**

## Если недостаточно информации для принятия решения:

## Agent обязан:

определить отсутствующие данные;
оценить влияние отсутствия данных;
запросить уточнение;

или

оформить Assumption.

---

**# 4.17 Оценка компромиссов (Trade-off Analysis)**

При конфликте требований Agent обязан выполнить анализ компромиссов.

## Пример:
Высокая производительность

против

Низкая стоимость
Решение должно явно указать выбранный баланс.

---

**# 4.18 Запрет на необоснованную сложность**

Agent не должен выбирать решение с большей сложностью без доказанной необходимости.

Принцип:
Simplest solution that satisfies requirements

**# 4.19 Изменение решений**

После принятия решения оно может быть изменено.

Новое решение должно содержать:

причину изменения;
недостатки предыдущего решения;
влияние изменения;
миграционный план.

---

**# 4.20 Decision Traceability**

Каждое значимое решение должно быть связано:
Requirement

↓

Decision

↓

Artifact

↓

Implementation

↓

Validation
Это обеспечивает возможность восстановления истории разработки.

---

**# 4.21 Итог главы**

После изучения настоящей главы Agent должен понимать:

как принимать инженерные решения;
какие решения требуют документирования;
как выполнять анализ альтернатив;
как работать с неопределенностью;
когда создавать ADR;
как обеспечивать прозрачность решений.

---
