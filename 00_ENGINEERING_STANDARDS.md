# Глава 1. Общие положения и терминология

## 1.1 Назначение документа

Настоящий документ определяет единые инженерные стандарты проекта AI Software Team.

Документ устанавливает:

- архитектурную модель агентной системы;
- правила организации процесса разработки;
- требования к качеству инженерных решений;
- правила формирования и передачи артефактов;
- единый словарь терминов;
- обязательные требования к работе всех агентов.

Настоящий стандарт является нормативным документом проекта.

Все агенты AI Software Team обязаны соблюдать требования настоящего документа.

---

# 1.2 Область применения

Настоящий стандарт применяется ко всем этапам жизненного цикла разработки программного обеспечения:

- сбор требований;
- анализ требований;
- проектирование архитектуры;
- планирование разработки;
- реализация программного кода;
- проверка качества;
- тестирование;
- подготовка к развертыванию;
- сопровождение.

Стандарт применяется независимо от:

- используемой языковой модели;
- программного языка;
- платформы разработки;
- области применения создаваемого продукта.

---

# 1.3 Архитектурная модель AI Software Team

AI Software Team использует четырехуровневую архитектурную модель:
Stage

↓

Contract

↓

Agent

↓

Artifact

Каждый уровень имеет строго определенное назначение.

---

## Stage

Stage — этап жизненного цикла разработки.

Stage определяет:

- цель этапа;
- место этапа в общем процессе разработки;
- необходимые входные данные;
- ожидаемый результат;
- критерии начала;
- критерии завершения.

Примеры Stage:

- Requirements Discovery Stage;
- Requirements Analysis Stage;
- Architecture Design Stage;
- Implementation Stage;
- Testing Stage.

---

## Contract

Contract — формальное описание взаимодействия между этапами.

Contract определяет:

- какие данные получает этап;
- какие данные формирует этап;
- требования к входным данным;
- требования к выходным данным;
- критерии приемки результата.

Contract является интерфейсом между этапами разработки.

Изменение контракта требует проверки совместимости всех связанных этапов.

---

## Agent

Agent — специализированный исполнитель, реализующий один или несколько контрактов.

Agent отвечает за выполнение конкретной инженерной функции.

Agent:

- получает входные артефакты;
- выполняет обработку;
- создает выходной артефакт;
- выполняет самопроверку результата.

Agent не изменяет область ответственности других агентов.

---

## Artifact

Artifact — результат выполнения этапа.

Artifact является единицей обмена информацией между агентами.

Примеры артефактов:

- requirements.json;
- SRS.md;
- architecture.md;
- roadmap.json;
- source code;
- review.md;
- test_report.md;
- deployment.md.

Каждый Artifact должен иметь:

- владельца;
- версию;
- статус;
- источник происхождения.

---

# 1.4 Принцип разделения ответственности

Каждый элемент архитектурной модели имеет собственную ответственность.
Stage

Определяет ЧТО должно быть выполнено.

↓

Contract

Определяет КАК осуществляется взаимодействие.

↓

Agent

Определяет КТО выполняет работу.

↓

Artifact

Определяет ЧТО является результатом.

Смешивание этих уровней запрещается.

Примеры неправильного подхода:

- описание требований внутри промпта агента вместо Contract;
- хранение решений только в сообщении чата вместо Artifact;
- изменение процесса разработки внутри конкретного Agent.

---

# 1.5 Приоритет документов

При принятии решений используется следующий порядок приоритетов:

1. PROJECT_CHARTER.md

2. AI_CONSTITUTION.md

3. 00_ENGINEERING_STANDARDS.md

4. Contract текущего Stage

5. Спецификация Agent

6. Входные Artifact

7. Локальные инструкции задачи

При обнаружении противоречий агент обязан:

- остановить выполнение конфликтующего действия;
- указать источник конфликта;
- предложить способ разрешения.

---

# 1.6 Основные инженерные принципы

Все решения проекта должны соответствовать следующим принципам.

---

## Прослеживаемость

Каждое решение должно иметь источник.

Допустимые источники:

- требование пользователя;
- бизнес-требование;
- техническое ограничение;
- архитектурное решение;
- стандарт проекта.

---

## Проверяемость

Каждый результат должен иметь критерии проверки.

Непроверяемые утверждения не могут считаться инженерными решениями.

---

## Воспроизводимость

При одинаковых входных данных процесс должен приводить к сопоставимому результату.

---

## Минимизация предположений

Если информации недостаточно, Agent обязан:

- запросить уточнение;
- либо оформить явное допущение.

Скрытые допущения запрещаются.

---

## Простота

Из нескольких решений предпочтение получает решение с минимальной сложностью при сохранении требований.

---

## Согласованность

Все Artifact проекта должны использовать:

- одинаковые термины;
- одинаковые идентификаторы;
- одинаковые правила оформления.

---

# 1.7 Терминология

## Проект

Совокупность всех Artifact, решений, исходного кода и процессов, направленных на создание программного продукта.

---

## Пользователь

Человек, который формирует требования, принимает ключевые решения и подтверждает результаты этапов.

---

## Требование

Описание необходимого свойства или поведения системы.

Требование должно быть:

- однозначным;
- проверяемым;
- непротиворечивым.

---

## Ограничение

Условие, которое уменьшает множество допустимых решений.

Примеры:

- бюджет;
- сроки;
- технология;
- законодательные требования.

---

## Допущение (Assumption)

Предположение, принятое при отсутствии полной информации.

Каждое допущение должно содержать:

- описание;
- причину;
- влияние;
- необходимость подтверждения.

---

## Риск

Возможное событие, которое может отрицательно повлиять на проект.

Риск описывается через:

- вероятность;
- влияние;
- стратегию снижения.

---

## Решение

Осознанный выбор одного варианта из нескольких возможных.

Инженерное решение должно содержать:

- контекст;
- варианты;
- выбранный вариант;
- обоснование;
- последствия.

---

## ADR (Architecture Decision Record)

Документированная запись архитектурного решения.

ADR содержит:

- проблему;
- контекст;
- варианты;
- принятое решение;
- последствия.

---

## Технический долг

Будущее обязательство по улучшению системы, возникшее из-за принятия упрощенного решения.

Каждый технический долг должен быть:

- зафиксирован;
- объяснен;
- оценен.

---

## Definition of Ready (DoR)

Набор критериев, определяющих готовность начала Stage.

---

## Definition of Done (DoD)

Набор критериев, определяющих завершение Stage.

---

# 1.8 Требования к терминологии

Все документы проекта обязаны использовать единый словарь.

Запрещается:

- вводить новые термины без необходимости;
- использовать разные термины для одного понятия;
- применять разговорные выражения в инженерных документах.

При введении нового термина он должен быть добавлен в настоящий раздел.

---

# 1.9 Версионирование

Все документы и Artifact должны поддерживать версионирование.

Рекомендуется использовать Semantic Versioning:

MAJOR.MINOR.PATCH

Где:

MAJOR — несовместимые изменения.

MINOR — новая функциональность.

PATCH — исправление ошибок.

---

# 1.10 Требования к инженерным документам

Каждый нормативный документ проекта должен содержать:

- название;
- назначение;
- версию;
- статус;
- область применения;
- дату изменения;
- связанные документы.

---
